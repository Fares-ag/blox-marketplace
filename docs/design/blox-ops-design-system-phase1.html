Blox operations platform · Phase 1 + shell + workspace overview

Blox Ops Design System

Foundation for the five staff portals (Admin, Super Admin, Dealer, Credit, Finance). Everything below is rendered with the real tokens, not mocked in an image, so a specimen here is what the component should look like in the product. Numbering follows the order the work should land in.

Palette locked teal ops Type IBM Plex Sans · Plex Sans Arabic · Plex Mono Source of truth today blox-ops-tokens.scss, blox-ops.scss (2 532 lines), status-styles.ts Breakpoints 480 · 640 · 900 · 1200 · 1600 Date 2026-09-06

What is there now

  • Two token vocabularies coexist: --blox-* plus a full set of --dm-* and vercel --primary-* aliases remapped to teal. Pages mix all three.
  • Three table implementations: OpsDataTable (13 files, string columns, ReactNode rows), ops-core Table (9 files, MUI), and the OpsCoreTable alias (5 files).
  • ops-core Button, Input, Select, StatusBadge, ConfirmDialog and EmptyState all wrap MUI, so MUI leaks into page content despite the shell-only rule.
  • Auth: login sits in OpsAuthLayout; forgot, reset and verify still use dm-auth-* with an inline <style> block.
  • Status pills exist twice (StatusBadge in ops-core with MUI Chip, and in ops-ui-v2) and four application states collapse to one grey "pending" look.

What Phase 1 changes

  • One vocabulary: --blox-* only, with a deprecation shim for the aliases for one release.
  • One OpsTable primitive with typed columns, selection, skeleton, empty, error, pagination and an automatic mobile card fallback.
  • ops-core re-based on SCSS classes; MUI stays in BloxShell (drawer, popover, badge) only.
  • One auth layout for login, forgot, reset, verify and MFA, with named states.
  • One StatusPill with a semantic variant per state; the 13 application statuses each map to a distinct, contrast-checked pair.
